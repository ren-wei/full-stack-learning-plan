# 备选项目：聊天室

> 定位：实时通信方向的玩具项目，重点练习 WebSocket、连接生命周期、消息可靠性和权限校验，而不是做一个完整的 IM 产品。
>
> 建议周期：1-2 周（MVP 3-5 天，进阶 3-5 天，整理 1-2 天）
>
> 前置能力：Spring Boot、PostgreSQL、Vue 3、Pinia，了解 JWT 和基础 HTTP 接口开发。

## 项目目标

- 能独立解释一次 WebSocket 连接从建立、鉴权、订阅、发消息到断开的完整过程
- 能区分“广播成功”和“消息可靠送达”，并为断线重连设计补偿
- 能在服务端完成房间权限校验，而不是只依赖前端隐藏按钮
- 能用测试证明两人同时在线时消息可见、非成员不能订阅、重复提交不会产生重复消息
- 形成一份能讲清楚的 README：启动方式、协议说明、边界和已知问题

## 技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Spring Boot 3、Spring WebSocket | 原生 WebSocket 或 STOMP，二选一，不要同时上 |
| 数据库 | PostgreSQL 16 | 用户、房间、成员、消息 |
| 缓存 | Redis（可选） | 在线状态、跨实例广播；MVP 可先不做 |
| 前端 | Vue 3 + Vite + Pinia | 登录、房间列表、聊天窗口 |
| 测试 | JUnit 5 + Spring Boot Test | 至少覆盖核心 WebSocket 集成流程 |

不要为了“像生产”一次性引入 Kafka、Elasticsearch 和微服务。先把单实例链路跑通，再通过 Redis 扩展。

## 功能范围

### MVP（必须完成）

- 用户名密码登录，复用已有 JWT 方案
- 房间列表：创建房间、加入房间、查看已加入房间
- 房间内发送文本消息，所有在线成员实时收到
- 拉取最近 50 条历史消息，并支持向上翻页
- 显示当前在线成员
- 断线后自动重连，重连成功后补齐缺失消息
- 消息发送失败时有明确提示，不静默丢失

### 进阶（选做）

- 私聊会话
- 未读数与最后已读位置
- 消息撤回（软删除 + 事件通知）
- 敏感词过滤或简单内容审核
- 多实例部署，使用 Redis Pub/Sub 广播
- 发送频率限制：单用户每秒最多 N 条
- 消息已读回执、正在输入状态
- 文件或图片消息（先做对象存储，不要把二进制塞进数据库）

### 明确不做

- 音视频通话
- 端到端加密
- 万人大群和复杂推送
- 自研 IM 协议或二进制编解码
- 完整的内容审核后台

## 里程碑

| 阶段 | 交付物 | 验收方式 |
| --- | --- | --- |
| M1 单机回声 | 建立连接后能收到自己发送的消息 | 两个浏览器窗口互发消息 |
| M2 房间与权限 | 房间列表、加入房间、非成员禁止发言 | 用接口或 WebSocket 客户端构造越权请求 |
| M3 消息持久化 | 消息落库，历史消息分页 | 重启服务后历史仍在 |
| M4 在线状态与重连 | 在线列表、断线重连、补消息 | 断网 10 秒再恢复，消息不丢不重 |
| M5 工程质量 | 集成测试、README、部署说明 | 新环境按文档可在 30 分钟内跑起来 |

## 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `app_user` | `id`、`username`、`password_hash`、`nickname`、`created_at` | 可以直接复用博客项目的用户体系 |
| `chat_room` | `id`、`name`、`owner_id`、`created_at` | 房间名是否唯一需要明确，不能默认“应该唯一” |
| `room_member` | `room_id`、`user_id`、`role`、`joined_at`、`last_read_message_id` | 联合主键防止重复加入 |
| `chat_message` | `id`、`room_id`、`sender_id`、`client_msg_id`、`content`、`type`、`seq`、`created_at`、`deleted` | `client_msg_id` 用于幂等 |
| `user_session`（可选） | `user_id`、`last_seen_at`、`connection_id` | 在线状态的简化实现 |

实现要点：

- `chat_message` 建立 `(room_id, seq)` 唯一索引，`seq` 是房间内单调递增序号
- `(room_id, sender_id, client_msg_id)` 唯一索引，防止网络重试产生重复消息
- 历史消息按 `room_id + seq desc` 查询，翻页使用 `beforeSeq` 游标，避免深分页
- 不要用数据库自增主键直接当房间内序号，也不要在前端生成可信的消息 ID
- 房间内 `seq` 可以用 PostgreSQL 序列或原子计数表分配；重复消息依赖唯一约束，必要时配合 `ON CONFLICT DO NOTHING`

## 接口与 WebSocket 协议

### HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/auth/login` | 登录并获取 access token |
| `GET` | `/api/rooms` | 房间列表 |
| `POST` | `/api/rooms` | 创建房间 |
| `POST` | `/api/rooms/{id}/join` | 加入房间 |
| `GET` | `/api/rooms/{id}/messages?beforeSeq=&size=50` | 历史消息 |
| `GET` | `/api/rooms/{id}/members` | 当前在线成员 |

### WebSocket 事件包

统一使用 JSON 信封，前后端按同一结构解析：

```json
{
  "version": 1,
  "type": "SEND_MESSAGE",
  "requestId": "c0a8012e-...",
  "roomId": 12,
  "payload": {
    "clientMsgId": "b7f1...",
    "content": "hello"
  },
  "timestamp": 1760000000000
}
```

| 方向 | 事件 | 作用 |
| --- | --- | --- |
| 客户端 → 服务端 | `JOIN_ROOM` | 订阅房间，服务端校验成员身份 |
| 客户端 → 服务端 | `LEAVE_ROOM` | 取消订阅 |
| 客户端 → 服务端 | `SEND_MESSAGE` | 发送消息，携带 `clientMsgId` |
| 客户端 → 服务端 | `PING` | 心跳 |
| 服务端 → 客户端 | `JOINED` | 订阅成功，返回当前 `seq` |
| 服务端 → 客户端 | `MESSAGE` | 新消息或补发消息 |
| 服务端 → 客户端 | `ACK` | 确认消息已落库，返回服务端消息 ID 和 `seq` |
| 服务端 → 客户端 | `ERROR` | 统一错误码和可读信息 |
| 服务端 → 客户端 | `PONG` | 心跳响应 |
| 服务端 → 客户端 | `PRESENCE` | 成员上线或下线 |

协议要求：

- 连接建立后先完成鉴权，未鉴权连接不能订阅或发送
- 所有事件包含 `requestId`，客户端据此匹配响应和超时
- 错误使用稳定错误码，例如 `AUTH_REQUIRED`、`NOT_ROOM_MEMBER`、`RATE_LIMITED`
- 服务端不能信任客户端传入的 `senderId`，只能从会话中取当前用户

## 关键实现顺序

1. 先做 HTTP 登录和房间 CRUD，确保权限模型清楚
2. 用单个房间跑通 WebSocket 广播，不落库
3. 加消息表和幂等约束，发送成功后返回 `ACK`
4. 加历史消息和重连补发，使用 `seq` 而不是时间戳做游标
5. 加在线状态、心跳和超时清理
6. 最后再考虑 Redis 和限流，不要一开始就上分布式

## 生产级关注点

### 鉴权与授权

- 握手阶段校验 token，并绑定用户身份到连接上下文
- 每次订阅和发送都校验房间成员关系，不能只在加入房间时校验一次
- 管理动作（踢人、删除房间）单独做角色判断
- 前端隐藏按钮不等于权限控制，接口和 WebSocket 事件都要校验

### 消息可靠性与顺序

- 先持久化再广播，还是先广播再异步落库，需要明确取舍并写进 README
- 单实例可以通过内存队列保证顺序；多实例必须给消息分配全局有序的 `seq`
- 重连时客户端携带最后收到的 `seq`，服务端补发之后的消息
- 消息重复到达时前端按服务端消息 ID 或 `clientMsgId` 去重

### 重连与幂等

- 指数退避重连，设置最大间隔和抖动，避免服务端故障时被重连风暴打垮
- 客户端发送超时后不能无限重试；使用 `clientMsgId` 让服务端识别重复请求
- 连接断开时保留草稿和未确认消息，恢复后按顺序重发
- 心跳超时和服务端主动关闭要区分处理，并记录原因

### 多实例扩展

- 单机内存广播只适合 MVP；多实例需要 Redis Pub/Sub、Redis Streams 或消息队列
- 在线状态使用带 TTL 的 key，进程崩溃后能自动过期
- 不要把“连接在哪台机器”写死在前端；网关或 Redis 负责路由
- 明确消息是至少一次还是至多一次，并在 UI 上体现

### 安全与内容

- 文本消息按纯文本渲染，禁止直接 `v-html`
- 限制消息长度、连接数、单用户发送频率
- 防止 SQL 注入、越权读取历史消息和房间枚举
- 日志中不要打印 token、密码和完整消息内容
- 文件消息要校验类型、大小和访问权限，使用临时签名 URL

### 可观测性与测试

- 记录连接数、在线用户数、消息吞吐、发送延迟、错误率和重连次数
- 给每条消息带 trace ID，便于串联客户端、网关和服务端日志
- 至少写两个 WebSocket 集成测试：正常互发、非成员发送被拒
- 手动测试断网、服务重启、重复点击发送、连续快速发送四种情况
- 压测只作为了解，不在玩具项目阶段追求高并发数字

## 验收标准

- [ ] 两个浏览器账号能进入同一房间并实时互发消息
- [ ] 非房间成员无法订阅或发送，服务端返回明确错误
- [ ] 刷新页面或重启服务后能看到历史消息
- [ ] 断网后恢复连接，缺失消息能补齐且不重复
- [ ] 重复提交同一条消息只产生一条记录
- [ ] 在线成员列表会随上下线变化
- [ ] 消息内容按纯文本展示，不能注入 HTML
- [ ] 有启动文档、协议说明和已知问题清单
- [ ] 至少有一个自动化集成测试覆盖核心链路

## 延伸方向

- 私聊与群聊统一会话模型
- 已读回执、未读数、消息搜索
- 撤回、编辑、回复引用
- 内容审核和举报处理
- 基于 Redis Streams 的消息分发
- 用 WebSocket 网关统一鉴权和限流
