# 备选项目：后台管理模板

> 定位：可复用的后台管理骨架，用来练习登录鉴权、RBAC、通用 CRUD 和前端工程化，而不是堆一堆业务页面。
>
> 建议周期：1-2 周（骨架与登录 3-4 天，权限与 CRUD 4-5 天，整理 1-2 天）
>
> 前置能力：Vue 3、Vue Router、Pinia、Element Plus、Spring Boot、PostgreSQL。

## 项目目标

- 形成一套可以复制到后续项目的管理端骨架，而不是一次性页面
- 理解登录态、路由权限、按钮权限、接口权限四者之间的关系
- 用统一响应、分页、错误处理和审计日志约束后端接口
- 在一个示例业务模块上完成查询、新增、编辑、禁用、删除的完整 CRUD 流程
- 输出模板文档，说明哪些部分是通用能力、哪些部分需要按业务替换

## 技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Spring Boot 3、MyBatis-Plus | 复用博客项目的登录和异常处理 |
| 数据库 | PostgreSQL 16 | 用户、角色、权限、审计日志 |
| 前端 | Vue 3 + Vite + TypeScript | 使用组合式 API |
| UI | Element Plus | 布局、表格、表单、弹窗、分页 |
| 状态 | Pinia | 登录用户、权限、菜单 |
| 测试 | JUnit 5、Vitest（可选） | 重点测试权限矩阵和接口契约 |

如果暂时不想写后端，可以先用 Mock 接口把前端骨架跑通，但最终至少要对一个真实模块完成前后端联调。

## 功能范围

### MVP（必须完成）

- 登录、退出、获取当前用户信息
- 后台布局：侧边栏、顶部栏、面包屑、内容区、错误页
- 路由守卫：未登录跳转登录页，无权限跳转 403
- 用户管理：搜索、分页、新增、编辑、禁用、重置密码
- 角色管理：角色 CRUD、给角色分配权限
- 菜单或权限点管理：至少能维护权限标识
- 按钮级权限：通过指令或组件控制按钮显示
- 一个示例业务模块（例如公告管理），证明模板可以复制
- 登录和关键变更操作写入审计日志
- 统一处理 401、403、404、500，以及加载、空数据、请求失败状态

### 进阶（选做）

- 后端下发动态菜单和动态路由
- access token + refresh token，刷新失败统一退出
- 数据权限：仅本人、本部门、全部
- 导入导出 Excel
- 文件上传与附件管理
- 主题切换、国际化
- Mock 模式，前后端可独立开发
- 请求取消、搜索防抖、表格列配置
- 操作日志展示变更前后内容
- 软删除与回收站

### 明确不做

- 低代码页面设计器
- 微前端
- 单点登录和复杂组织架构同步
- 多租户
- 完整工作流引擎

## 里程碑

| 阶段 | 交付物 | 验收方式 |
| --- | --- | --- |
| M1 项目骨架 | Vite 工程、目录结构、布局、路由 | 能进入首页并在菜单间切换 |
| M2 登录与用户 | 登录、当前用户、退出、用户列表 | 未登录访问后台会跳转登录页 |
| M3 RBAC | 角色、权限、菜单、按钮权限 | 不同角色看到的菜单和按钮不同 |
| M4 示例 CRUD | 公告管理的完整增删改查 | 搜索、分页、表单校验、错误提示都可用 |
| M5 工程收尾 | 审计日志、README、部署说明 | 新人按文档可以启动并新增一个模块 |

## 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `sys_user` | `id`、`username`、`password_hash`、`nickname`、`status`、`created_at` | `username` 唯一；密码只存哈希 |
| `sys_role` | `id`、`code`、`name`、`status` | 角色编码稳定，名称可改 |
| `sys_permission` | `id`、`code`、`name`、`type`、`parent_id` | `type` 区分菜单、按钮、接口权限 |
| `sys_user_role` | `user_id`、`role_id` | 联合主键 |
| `sys_role_permission` | `role_id`、`permission_id` | 联合主键 |
| `sys_audit_log` | `id`、`operator_id`、`action`、`target_type`、`target_id`、`result`、`detail`、`ip`、`created_at` | 追加写入，不修改历史 |
| `sys_dept`（可选） | `id`、`name`、`parent_id` | 做数据权限时再加 |

实现要点：

- 用户名、角色编码、权限编码建立唯一索引
- 删除用户优先使用禁用或软删除，避免破坏历史审计记录
- 审计日志只追加，不提供编辑和删除接口
- 权限编码使用稳定命名，例如 `user:read`、`user:create`、`user:update`、`user:disable`
- 列表查询为常用过滤字段建立索引，分页大小设置上限

## 接口约定

### 统一响应

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "traceId": "8f3c..."
}
```

### 分页响应

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "records": [],
    "page": 1,
    "pageSize": 20,
    "total": 0
  },
  "traceId": "8f3c..."
}
```

约定要求：

- HTTP 状态码表达协议层结果：`401` 未登录、`403` 无权限、`404` 不存在、`409` 冲突、`422` 参数错误、`500` 服务异常
- 业务错误码表达领域结果，例如 `USER_DISABLED`、`ROLE_IN_USE`、`PERMISSION_DENIED`
- 参数校验在服务端完成，前端校验只负责交互体验
- 列表接口统一使用 `page`、`pageSize`、`keyword`、`status`、`sort`，并限制 `pageSize` 最大值
- 创建接口用唯一约束防止重复，不依赖“先查再插”避免并发漏洞
- 更新接口携带版本号或 `updated_at`，防止覆盖他人的修改（按需）

### 主要接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/auth/login` | 登录 |
| `POST` | `/api/auth/logout` | 退出并失效登录态 |
| `GET` | `/api/auth/me` | 当前用户、角色和权限 |
| `GET` | `/api/users` | 用户分页查询 |
| `POST` | `/api/users` | 新增用户 |
| `PUT` | `/api/users/{id}` | 编辑用户 |
| `PATCH` | `/api/users/{id}/status` | 启用或禁用 |
| `GET` | `/api/roles` | 角色列表 |
| `PUT` | `/api/roles/{id}/permissions` | 分配权限 |
| `GET` | `/api/audit-logs` | 审计日志查询 |

## 前端目录建议

```text
src/
  api/            # 按业务域拆分的请求函数
  components/     # 通用组件：分页表格、搜索表单、状态标签
  layouts/        # 后台布局
  router/         # 路由表、守卫、动态路由
  stores/         # 登录用户、权限、菜单
  types/          # 接口和实体的类型定义
  utils/request/  # axios 实例、拦截器、错误处理
  views/          # 页面
  directives/     # v-permission 等指令
```

不要把所有请求塞进一个 `api.js`，也不要在组件里直接写 `axios.get()`。请求函数、类型和错误处理要分层。

## 生产级关注点

### 权限模型

- 菜单权限控制“能不能看到入口”，接口权限控制“能不能执行”，二者必须同时校验
- 按钮权限只改善体验，不能替代后端鉴权
- 默认拒绝：没有明确授权的接口一律不可访问
- 前端路由守卫防止误入页面，后端仍然要对每个接口做权限判断
- 给权限变更写审计日志，并明确变更何时生效
- 用权限矩阵测试不同角色，而不是只手动点几个按钮

### 登录态与安全

- 密码使用 BCrypt 或 Argon2 哈希，禁止明文、可逆加密和日志输出
- access token 短有效期，refresh token 单独存储并支持轮换和撤销
- 明确 token 放在 localStorage 还是 HttpOnly Cookie，并说明 XSS、CSRF 的取舍
- 退出登录要让服务端 token 或会话失效，不能只清前端缓存
- 登录失败做频率限制，避免暴力破解
- 管理端与普通用户端使用不同的权限边界

### 数据完整性

- 用户禁用后已登录会话如何处理，需要明确策略
- 删除角色前检查是否仍被用户引用，返回 `ROLE_IN_USE` 而不是级联删除
- 唯一约束和事务是最后防线，不能只靠前端校验
- 审计日志记录操作者、动作、目标、结果、时间和来源 IP
- 敏感字段（密码、token、身份证号）不能进入日志和前端缓存

### 查询与性能

- 列表接口必须分页，禁止无上限 `findAll`
- 避免 `select *`、循环查库和 N+1 查询
- 为高频过滤条件建立组合索引，并用 `EXPLAIN ANALYZE` 验证
- 前端表格请求要处理竞态：旧请求晚返回时不能覆盖新结果
- 大导出使用异步任务或流式下载，不在请求线程里无限拼内存

### 前端工程质量

- axios 统一封装：注入 token、处理 401、统一错误提示、附加 trace ID
- 401 刷新 token 使用单飞（single-flight），避免并发请求同时刷新
- 路由懒加载，按模块拆分打包
- 表格、表单、弹窗封装成可复用组件，但不要过度抽象成“万能组件”
- 统一处理 loading、empty、error 三种状态
- 错误页和权限页要能直接访问，不能依赖登录态

### 可观测性与测试

- 每个响应带 trace ID，前端报错时提示用户可复制该 ID
- 记录登录失败、权限拒绝、关键配置变更的数量
- 后端至少测试：登录、越权访问、用户 CRUD、角色引用检查
- 前端至少测试：路由守卫、权限指令、请求拦截器
- 准备一份“新增一个业务模块”的检查清单，验证模板真的可复用

## 验收标准

- [ ] 未登录访问后台会跳转登录页，登录后可返回原页面
- [ ] 不同角色看到的菜单和按钮不同，直接调用越权接口会被拒绝
- [ ] 用户、角色、示例业务模块都能完成分页查询和增删改查
- [ ] 表单错误有字段级提示，接口错误有统一提示
- [ ] 禁用用户后无法继续登录或继续使用旧会话
- [ ] 角色仍被用户引用时不能删除，并返回明确错误
- [ ] 关键操作写入审计日志，日志不可在前端修改
- [ ] 刷新页面后登录态和动态路由能正确恢复
- [ ] README 说明如何新增一个模块、如何配置权限、如何部署
