# 备选项目：审批流程

> 定位：业务建模和状态机方向的玩具项目，以“请假审批”为载体，练习多级审批、条件分支、并发处理和审计追踪。
>
> 建议周期：1-2 周（单级审批 3-4 天，多级与条件分支 4-5 天，测试与整理 2-3 天）
>
> 前置能力：Spring Boot、PostgreSQL、Vue 3，了解事务、乐观锁和基本权限模型。

## 项目目标

- 能把一个真实业务拆成业务表单、流程实例、审批任务、审批记录四部分
- 能用显式状态机管理状态，避免 `if/else` 散落在各个 Service 中
- 能正确处理重复提交、并发审批、驳回、撤回和条件分支
- 留下完整审计轨迹，任何状态变化都能回答“谁在什么时候做了什么”
- 为后续理解 BPMN 和流程引擎打基础，但玩具阶段不引入流程引擎

## 技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Spring Boot 3、MyBatis-Plus | 复用博客项目的登录、异常和权限基础 |
| 数据库 | PostgreSQL 16 | 业务表单、流程实例、任务、审批记录 |
| 前端 | Vue 3 + Element Plus | 我的申请、待办、已办、详情时间线 |
| 状态管理 | 显式状态机（代码实现） | 不引入 Activiti、Flowable 等引擎 |
| 测试 | JUnit 5 | 表驱动测试状态迁移和权限 |

## 功能范围

### MVP（必须完成）

- 员工填写请假申请：类型、开始时间、结束时间、天数、原因
- 提交后进入待审批状态，生成主管审批任务
- 主管同意或驳回，填写审批意见
- 我的申请、待办任务、已办任务列表
- 申请详情页展示审批时间线
- 驳回后流程结束，申请人可以修改并重新发起
- 待审批且无人处理时，申请人可以撤回
- 所有状态变化写入审批记录，禁止覆盖历史

### 进阶（选做）

- 多级审批：请假超过 3 天时，主管通过后增加 HR 审批
- 条件分支：按请假类型或天数选择不同审批链
- 会签（全部同意才通过）或或签（一人同意即通过）
- 转交、委托和代理审批
- 超时提醒、自动升级
- 附件上传与下载权限
- 站内信或邮件通知
- 已通过申请的撤销（需要单独权限和审计）

### 明确不做

- 可视化流程设计器
- 任意 BPMN 流程编排
- 完整组织架构同步
- 多租户
- 完整 HR 或考勤系统

玩具项目的价值在于把状态和并发做对，不在于支持任意流程。

## 里程碑

| 阶段 | 交付物 | 验收方式 |
| --- | --- | --- |
| M1 单级审批 | 提交、同意、驳回、时间线 | 一条申请完整走完三种结果 |
| M2 权限与撤回 | 待办隔离、越权拒绝、撤回 | 其他用户看不到也处理不了别人的待办 |
| M3 多级与分支 | 超过 3 天增加 HR 审批 | 不同天数生成不同任务链 |
| M4 并发与幂等 | 乐观锁、重复审批保护 | 两个请求同时审批只有一个成功 |
| M5 工程质量 | 状态机测试、README、演示数据 | 状态迁移表全部有对应测试 |

## 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `leave_request` | `id`、`applicant_id`、`leave_type`、`start_at`、`end_at`、`days`、`reason`、`status`、`version`、`created_at`、`updated_at` | 业务表单，保存展示所需快照 |
| `approval_instance` | `id`、`business_type`、`business_id`、`status`、`current_step`、`version`、`started_at`、`finished_at` | 流程实例，状态以这里为准 |
| `approval_task` | `id`、`instance_id`、`step_no`、`assignee_id`、`status`、`decision`、`comment`、`due_at`、`acted_at`、`version` | 一个审批人一个任务 |
| `approval_record` | `id`、`instance_id`、`task_id`、`operator_id`、`action`、`from_status`、`to_status`、`comment`、`created_at` | 只追加，不修改、不删除 |
| `approval_rule`（可选） | `business_type`、`step_no`、`condition`、`approver_role` | 规则简单时先用代码策略，不必建表 |

实现要点：

- `approval_instance` 对 `(business_type, business_id)` 建立唯一约束，避免同一业务生成多个活动实例
- `approval_task` 对 `(instance_id, step_no, assignee_id)` 建立唯一约束，避免重复生成任务
- 任务表保留 `assignee_id` 快照；组织架构变化时是否改派必须明确，不能让历史审批人凭空变化
- `leave_request.status` 只用于列表查询和展示，状态迁移以流程实例为准，二者在同一事务内更新
- 审批记录不提供更新和删除接口，数据库账号也不应具备随意改历史的权限

## 状态机

### 申请状态

| 当前状态 | 动作 | 下一状态 | 允许角色 | 说明 |
| --- | --- | --- | --- | --- |
| `DRAFT` | 提交 | `PENDING` | 申请人 | 校验表单完整性和时间范围 |
| `PENDING` | 当前节点同意且还有下一步 | `PENDING` | 当前审批人 | 创建下一步任务 |
| `PENDING` | 最后一步同意 | `APPROVED` | 当前审批人 | 写入结束时间 |
| `PENDING` | 驳回 | `REJECTED` | 当前审批人 | 剩余任务全部取消 |
| `PENDING` | 撤回 | `WITHDRAWN` | 申请人 | 仅无人处理时允许 |
| `APPROVED` | 撤销（选做） | `REVOKED` | 有权限的管理者 | 必须单独记审计 |

非法迁移统一返回 `409 INVALID_STATE_TRANSITION`，不能静默忽略，也不能用“更新成功”掩盖状态错误。

### 任务状态

`PENDING → APPROVED`、`PENDING → REJECTED`、`PENDING → CANCELLED`、`PENDING → EXPIRED`（选做）。

任务状态和实例状态分开：任务描述“某个人要做什么”，实例描述“整条流程走到哪里”。

## 接口草案

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/leave-requests` | 创建草稿 |
| `PUT` | `/api/leave-requests/{id}` | 修改草稿 |
| `POST` | `/api/leave-requests/{id}/submit` | 提交审批 |
| `POST` | `/api/leave-requests/{id}/withdraw` | 撤回申请 |
| `GET` | `/api/leave-requests/mine` | 我的申请 |
| `GET` | `/api/approval-tasks/pending` | 我的待办 |
| `GET` | `/api/approval-tasks/done` | 我的已办 |
| `POST` | `/api/approval-tasks/{id}/approve` | 同意 |
| `POST` | `/api/approval-tasks/{id}/reject` | 驳回 |
| `GET` | `/api/leave-requests/{id}` | 详情与审批时间线 |

请求中不要接受客户端传入的 `assigneeId`、`fromStatus`、`toStatus` 等可信字段。当前用户从登录态获取，状态由服务端计算。

## 并发、事务与幂等

### 并发审批

两个人同时点击同意时，只能有一个请求成功：

```sql
UPDATE approval_task
SET status = 'APPROVED', decision = 'APPROVE', comment = ?, acted_at = ?, version = version + 1
WHERE id = ? AND status = 'PENDING' AND version = ?;
```

受影响行数为 0 时返回 `409 TASK_ALREADY_HANDLED`，然后重新查询并展示最新状态。不要用“先查询再更新”作为唯一保护。

PostgreSQL 可以用 `UPDATE ... RETURNING` 直接拿到迁移后的任务记录，但状态条件仍必须写在 `WHERE` 中，不能退化成“先查再改”。

### 重复提交

- 提交和审批接口支持 `Idempotency-Key`，或通过当前状态判断重复请求
- 同一个审批请求重复到达时，要么返回相同结果，要么返回明确的“已处理”，不能生成第二条记录
- 前端按钮置灰只能改善体验，不能替代服务端幂等

### 事务边界

- 业务表单状态、流程实例、任务状态、审批记录必须在同一事务中更新
- 通知、邮件、消息推送不要在事务内同步调用；使用 outbox 或提交后事件
- 事务中避免远程调用和长时间等待
- 每个状态迁移写成独立方法，并在入口处统一校验权限和当前状态

## 生产级关注点

### 权限与审批人

- 只有任务指定的 `assignee_id` 能处理任务，角色相同不代表可以代审
- 申请详情只对申请人、当前审批人和有审计权限的管理者可见
- 审批人离职或组织调整时，需要明确的转交或改派策略
- 管理员“代操作”必须单独授权并写审计，不能悄悄伪装成审批人
- 前端不传审批人，审批人由服务端根据规则和快照计算

### 规则与可配置性

- 规则包括步骤数、审批人来源、条件表达式和通过策略
- 玩具项目先用代码策略或简单配置表，不要一开始实现通用表达式引擎
- 规则变更要版本化；进行中的流程应使用启动时的规则快照还是最新规则，必须明确
- 审批人信息在任务创建时落快照，保证历史可解释
- 条件分支要有默认分支和兜底策略，避免出现无人可审

### 业务校验

- 结束时间必须晚于开始时间
- 请假天数由服务端计算，不能直接信任前端传入
- 明确是否扣除周末和法定节假日，并写进 README
- 同一时间段是否允许重复请假，需要业务决定并落实为约束
- 提交时校验必填项，草稿允许不完整

### 审计与可追溯

- 记录动作、操作者、原状态、新状态、意见、时间和来源
- 记录谁创建了任务、任务分配给了谁、是否发生过改派
- 审批记录只追加，任何撤销都是新记录，不删除旧记录
- 日志和审计中不要泄露敏感附件或完整个人信息
- 能按申请 ID 还原完整时间线，且时间线顺序稳定

### 通知与可靠性

- 通知失败不能导致审批失败，使用 outbox 表或消息队列重试
- 消费方必须幂等，重复通知最多让用户多看一条，不能重复建任务
- 超时提醒要基于任务截止时间，而不是前端定时器
- 记录通知发送结果和重试次数，便于排查

### 可观测性与测试

- 记录各状态数量、待办平均停留时间、审批时长、驳回率和超时任务数
- 状态迁移测试使用表驱动：当前状态 × 动作 × 角色 → 期望结果
- 至少测试：越权审批、重复审批、并发审批、撤回后审批、非法迁移
- 用两个并发请求验证乐观锁，不要只靠人工点击
- 对进行中的流程做定时扫描，发现“有实例无待办任务”的异常数据

## 验收标准

- [ ] 申请人能创建、修改、提交和撤回草稿
- [ ] 主管能在待办中看到任务并同意或驳回，填写意见后时间线完整
- [ ] 非指定审批人无法处理任务，即使拥有相同角色
- [ ] 请假超过 3 天时，主管通过后正确生成 HR 审批任务
- [ ] 驳回后剩余任务被取消，申请不能再继续审批
- [ ] 两个并发审批请求只有一个成功，另一个得到明确冲突提示
- [ ] 重复提交不会产生重复流程实例或重复任务
- [ ] 非法状态迁移返回明确错误，而不是静默成功
- [ ] 审批记录只追加，能还原完整历史
- [ ] 状态迁移、权限和并发场景都有自动化测试

## 延伸方向

- 通用流程定义和规则版本化
- 会签、或签、加签、转交和委托
- 超时升级与 SLA 统计
- 与消息中心、组织架构和 HR 系统集成
- 基于领域事件拆分通知和报表
- 在理解状态机后再学习 BPMN 和 Flowable
