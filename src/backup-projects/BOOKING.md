# 备选项目：预约订座系统

> 定位：时间与资源竞争方向的玩具项目，重点练习时间段建模、并发占位、取消释放和时区处理，而不是做一个完整的酒店或票务系统。
>
> 建议周期：1-1.5 周（资源与时段 3-4 天，预约与并发 4-5 天，测试与收尾 2-3 天）
>
> 前置能力：Spring Boot、PostgreSQL、Vue 3，了解事务、条件更新和时间处理。

## 项目目标

- 能把资源、营业时间、可预约时段和预约记录分成清晰的模型
- 能用数据库约束和条件更新解决同一时段被多人同时抢占的问题
- 能处理容量大于 1、重复预约、取消释放、过期时段和后台关闭时段
- 能明确时间存储、展示和跨时区转换的边界
- 能用并发测试证明同一个座位不会超卖，取消后能正确释放

## 在本套作品中的位置

预约模块负责工作室的座位、房间或服务时段，复用后台模板的登录、RBAC、菜单和审计。它可以调用通知模块发送预约提醒，服务完成后可以生成问卷链接收集反馈。

预约模块只保存用户、资源和预约数据，不直接修改问卷或通知表。跨模块动作通过事件或 outbox 完成。

## 功能范围

### MVP（必须完成）

- 后台资源管理：座位、房间或服务项目，配置时段容量、最大接待人数和位置
- 后台营业时间配置：按星期设置开放时间和时段长度
- 自动生成未来 30 天的可预约时段
- 用户选择资源、日期和时段，创建预约
- 同一时段支持多个预约单元，例如开放区座位或独立包间
- 我的预约、预约详情、取消预约
- 后台预约列表、日历视图、关闭时段、标记完成或未到店
- 取消截止时间，例如开始前 2 小时不能自助取消
- 用户只能取消自己的预约，后台操作写审计日志
- 预约成功后发送提醒（可选，通过通知模块）

### 进阶（选做）

- 重复营业时间、节假日和临时停业
- 时段之间的缓冲时间
- 候补队列和自动补位
- 二维码签到
- 定金或押金支付
- 多资源组合预约，例如房间加设备
- 多时区展示和夏令时处理
- 用户信用分和爽约惩罚

### 明确不做

- 酒店房态、航班库存和复杂票务
- 动态定价和收益管理
- 完整排队叫号系统
- 复杂 POS 和会员体系

## 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `bk_resource` | `id`、`code`、`name`、`type`、`slot_capacity`、`max_party_size`、`location`、`timezone`、`status`、`created_at` | `code` 唯一；`slot_capacity` 是每时段预约单元数，`max_party_size` 是单次预约人数上限 |
| `bk_business_hours` | `id`、`resource_id`、`day_of_week`、`open_time`、`close_time`、`slot_minutes` | 按星期配置营业时间 |
| `bk_slot` | `id`、`resource_id`、`start_at`、`end_at`、`capacity`、`booked_count`、`status`、`version` | `(resource_id, start_at)` 唯一 |
| `bk_booking` | `id`、`booking_no`、`resource_id`、`slot_id`、`user_id`、`party_size`、`status`、`version`、`created_at`、`cancelled_at` | `booking_no` 唯一 |
| `bk_booking_log` | `id`、`booking_id`、`action`、`operator_id`、`from_status`、`to_status`、`created_at` | 状态变化只追加 |

关键约束：

- `bk_slot` 的 `(resource_id, start_at)` 唯一，保证重复生成时段不会产生重复记录
- `bk_slot.capacity` 和 `booked_count` 必须满足 `0 <= booked_count <= capacity`
- `bk_slot.capacity` 表示该时段能并存的预约单元数，`bk_booking.party_size` 表示单次预约人数，二者不是同一个概念
- 生成时段时从 `bk_resource.slot_capacity` 复制容量，必要时允许后台单独覆盖某个时段
- 创建预约时校验 `party_size <= bk_resource.max_party_size`，每次预约占用一个时段单元
- 同一用户同一时段只允许一个有效预约，可以用生成列唯一索引实现：

```sql
active_flag BOOLEAN GENERATED ALWAYS AS (
  CASE WHEN status = 'CONFIRMED' THEN TRUE ELSE NULL END
) STORED,
UNIQUE (user_id, slot_id, active_flag)
```

PostgreSQL 的唯一索引允许多个 `NULL`，因此取消后的历史记录不会阻止用户重新预约。不支持生成列的版本可以改用单独的 active 预约表或应用层锁。

- `bk_booking` 建立 `(user_id, created_at)` 和 `(slot_id, status)` 索引
- `bk_slot` 建立 `(resource_id, start_at, status)` 索引，按日期查询不会全表扫描

## 时段建模

推荐预先为未来 30 天生成时段，而不是每次请求时临时计算。原因：

- 后台可以单独关闭某个时段，而不改营业时间
- 条件更新可以直接锁定时段行，并发控制更简单
- 日历查询和容量统计更直接
- 唯一索引可以防止定时任务重复生成

生成规则：

1. 按资源的营业时间计算起止时间
2. 每个时段有独立的 `start_at`、`end_at` 和容量
3. 生成任务每天补齐未来 30 天，使用唯一索引保证幂等
4. 已开始的时段不能预约，历史时段保留用于统计
5. 时区在资源上配置，时间字段使用 `timestamptz` 存 UTC，展示时转换

## 核心流程

### 创建预约

1. 校验登录态、资源状态、时段未开始和人数不超过资源最大接待人数
2. 在事务中执行时段占位条件更新
3. 影响行数为 0 时返回 `409 SLOT_FULL` 或 `409 SLOT_CLOSED`
4. 插入预约记录，若违反同一用户同一时段唯一约束则回滚占位
5. 写入预约日志，提交事务
6. 事务提交后发送提醒，不阻塞预约结果

```sql
UPDATE bk_slot
SET booked_count = booked_count + 1,
    version = version + 1
WHERE id = ?
  AND status = 'OPEN'
  AND start_at > now()
  AND booked_count < capacity;
```

### 取消预约

1. 校验预约属于当前用户，且仍在取消截止时间内
2. 条件更新 `CONFIRMED → CANCELLED`
3. 只有状态迁移成功的请求才释放时段容量
4. 释放时使用 `booked_count > 0` 条件，避免负库存
5. 重复取消返回当前状态，不重复释放

### 后台关闭时段

- 如果时段没有有效预约，直接改为 `CLOSED`
- 如果已有预约，明确策略：拒绝关闭，或关闭后逐个取消并通知用户
- 关闭操作必须写审计日志，不能静默影响用户
- 已成立的预约不能因为后台关闭而凭空消失

### 完成与未到店

- 到店后由后台标记 `COMPLETED`
- 未到店标记 `NO_SHOW`，是否释放容量由业务决定
- 两种状态都保留预约记录，用于统计和信用管理
- 状态迁移只允许从 `CONFIRMED` 出发，重复操作返回明确结果

## 生产级关注点

### 并发与重复预约

- 条件更新是主要保护，唯一索引是最后防线
- 不能依赖“查询余量 → 判断 → 插入”的流程，因为并发请求会同时通过判断
- 同一用户重复点击要返回同一条预约，或返回明确的“已有预约”
- 取消和释放容量必须幂等，不能因为重试把容量加回去两次
- 用 50 个并发请求抢同一个时段，验证只有一个成功

### 时间与时区

- 数据库存 UTC，接口输出 ISO 8601，前端按资源时区展示
- 日期边界、营业时间跨午夜和夏令时必须明确处理
- 取消截止时间以服务端时间为准，不能相信客户端时间
- 定时生成时段和提醒任务要避免重复执行
- 所有时间比较使用统一时钟源，测试中可注入固定时钟

### 容量与业务规则

- 容量表示可并存的预约单元数，每次预约默认占用一个单元，除非业务明确一次占多个
- 人数不能超过资源的最大接待人数；人数和容量要区分清楚
- 候补、超售和释放策略要写进 README
- 关闭时段、节假日和临时停业的优先级要明确
- 爽约是否释放容量必须由业务决定，不能默认覆盖历史数据

### 权限与安全

- 用户只能查看和取消自己的预约，不能通过修改 `bookingId` 操作他人预约
- 后台资源、时段、预约分别设置权限码
- 公开预约页也要限流，防止脚本批量占位
- 预约备注和用户信息不能出现在公开日历中
- 敏感操作写审计日志，日志不包含完整手机号和备注

### 可观测性与测试

- 记录预约成功率、冲突率、取消率、爽约率、时段利用率和生成任务耗时
- 对“有资源但无时段”“时段容量小于已预约数”等异常数据做巡检
- 至少测试：并发抢同一时段、容量边界、重复预约、取消截止时间、关闭时段、时区转换
- 测试使用固定时钟，避免依赖真实当前时间导致偶发失败
- 用真实 PostgreSQL（Testcontainers `PostgreSQLContainer`）验证条件更新和唯一约束，内存数据库无法覆盖这些行为

## 验收标准

- [ ] 50 个并发请求抢同一个容量为 1 的时段，只有 1 个成功
- [ ] 容量为 4 的时段可以成功创建 4 个预约，第 5 个收到明确冲突错误
- [ ] 同一用户重复点击不会产生两条有效预约
- [ ] 用户取消后容量正确释放，重复取消不会重复释放
- [ ] 超过取消截止时间后，自助取消被拒绝
- [ ] 已开始的时段不能预约，关闭的时段不能预约
- [ ] 后台关闭已有预约的时段时，行为符合事先定义的策略
- [ ] 用户无法查看或取消他人的预约
- [ ] 数据库中的 UTC 时间与页面展示时间转换正确
- [ ] 有并发测试、时区边界测试、启动文档和演示数据
