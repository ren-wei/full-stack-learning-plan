# 备选项目：整套作品设计

> 定位：把后台管理模板、四个核心业务模块和可选的视频播放模块组合成一套可运行、可演示、可讲解的作品，而不是一堆互不相关的 demo。
>
> 建议周期：核心 8-10 周；如果加视频模块，再预留 1-1.5 周。按每周 10-15 小时估算，可以先做 6 周精简版，再补高级功能。
>
> 前置能力：完成阶段三、阶段四，能够独立完成 Spring Boot + Vue 3 前后端联调；备选项目数据库统一使用 PostgreSQL 16，与阶段三主线一致。
>
> 章节定位：本目录作为主线之外的备选项目，可从目录或总览进入，不影响阶段计划。

## 作品包装

建议包装成“校园文创工作室运营平台”：

- 工作室销售周边商品，需要订单、库存和履约
- 设计师向客户交付设计稿、发票和素材，需要文件上传与短链分享
- 客户预约拍摄、咨询或座位，需要预约订座
- 工作室收集售后反馈和活动报名，需要问卷系统
- 工作室展示作品集、课程回放或客户预览，需要视频播放器
- 管理员统一登录、分配角色、查看审计和运营概览，使用后台管理模板

这个业务故事能自然串起四个核心模块，视频播放器作为可选扩展，面试时也容易解释“为什么做这些功能”，而不是堆砌技术名词。

一句话描述：

> 独立设计并实现一套面向校园文创工作室的模块化单体运营平台，包含订单库存、文件分享、预约订座和问卷四个核心业务模块，并提供可选的视频播放模块，统一使用 Spring Boot、Vue 3、PostgreSQL、Redis、MinIO 和 Docker Compose。

## 设计原则

- **模块化单体**：一个 Spring Boot 应用、一个 Vue 应用、一套数据库，按业务模块分包，不拆微服务
- **一个后台**：登录、RBAC、菜单、审计、通用 CRUD 全部复用后台模板
- **公共能力下沉**：文件、短链、通知、幂等、审计、统一响应只实现一次
- **模块边界清晰**：模块之间只传 ID 或事件，不直接访问对方的 Mapper 和表
- **先正确再扩展**：先保证事务、并发和权限正确，再考虑缓存、队列和分布式
- **每模块一个硬问题**：订单练超卖，文件练分片，预约练并发，问卷练版本与校验，视频练转码与播放鉴权

## 模块边界

| 模块 | 负责内容 | 对外能力 | 主要依赖 |
| --- | --- | --- | --- |
| `system` | 登录、用户、角色、权限、菜单、审计 | JWT、权限码、审计日志 | 无 |
| `file` | 文件元数据、对象存储、上传会话、下载 | `upload`、`download`、`fileId` | MinIO、PostgreSQL |
| `share` | 短码、过期、撤销、使用次数 | 创建短链、解析短链 | PostgreSQL、Redis 可选 |
| `order` | 订单生命周期、订单项、履约 | 创建、支付、取消、发货 | `inventory`、`system`、`file` 可选 |
| `inventory` | 商品、SKU、库存、库存流水 | 锁定、确认、释放、调整 | PostgreSQL |
| `booking` | 资源、营业时间、时段、预约 | 查时段、创建、取消、管理 | `system`、通知模块可选 |
| `survey` | 问卷、题目、回答、统计 | 发布、填写、统计、导出 | `share`、`system`、`file` 可选 |
| `video` | 视频元数据、转码任务、HLS 播放、观看进度 | 创建视频、播放凭证、进度 | `file`、`system`、FFmpeg |
| `notification` | outbox、站内信、提醒 | 提交后通知、重试、死信 | PostgreSQL、可选邮件 |

订单模块需要商品和库存，可以把商品与库存放在同一个 `commerce` 业务域中，但订单和库存的职责仍要分开。示例中拆成 `order` 和 `inventory`，是为了强调“订单不能直接改库存表”这一边界。

视频模块是可选第五模块，不进入四个核心模块的首版闭环。它依赖文件模块保存源视频、封面和字幕，依赖 FFmpeg 做转码，适合在核心模块完成后追加。

## 技术栈

| 层次 | 选型 |
| --- | --- |
| 后端 | Java 17、Spring Boot 3、MyBatis-Plus、Bean Validation |
| 数据库 | PostgreSQL 16 |
| 缓存与短链 | Redis 7（可选，先保证数据库正确） |
| 对象存储 | MinIO（S3 兼容） |
| 前端 | Vue 3、Vite、TypeScript、Vue Router、Pinia、Element Plus |
| 视频 | FFmpeg、HLS.js、原生 `<video>` |
| 图表 | ECharts（运营概览和问卷统计） |
| 部署 | Docker Compose、Nginx |
| 测试 | JUnit 5、Testcontainers、Vitest 或 Playwright（可选） |
| 文档 | Markdown、OpenAPI、Mermaid 或 draw.io |

不引入 Kubernetes、服务网格、消息队列和 Elasticsearch。它们不是这套作品的核心，反而会稀释对业务正确性的讲解。

## 工程结构

后端按业务模块分包：

```text
src/main/java/com/example/platform/
  common/          # 统一响应、异常、分页、trace ID、幂等、审计
  system/          # 登录、用户、角色、权限、菜单
  file/            # 文件与对象存储
  share/           # 短链
  inventory/       # 商品、SKU、库存
  order/           # 订单与履约
  booking/         # 资源、时段、预约
  survey/          # 问卷、题目、回答、统计
  video/           # 视频、转码、HLS、播放进度
  notification/    # outbox、提醒、站内信
```

每个模块内部保持简单分层：

```text
controller/        HTTP 接口
application/       用例编排、事务边界
domain/            实体、状态机、领域规则
infrastructure/    Mapper、对象存储、外部适配
dto/               请求和响应对象
```

前端一个应用、两套布局：

```text
src/
  layouts/         AdminLayout、PublicLayout
  modules/         system、order、inventory、file、booking、survey、video
  components/      通用表格、表单、上传、状态标签、空状态
  api/             按模块拆分的请求函数
  router/          后台路由和公开路由
  stores/          登录用户、权限、菜单
  utils/request/   axios 封装和错误处理
```

公开页面建议：

- `/s/{code}`：文件分享页或问卷填写页，由短链的 `target_type` 决定
- `/book/{resourceCode}`：公开预约页，登录后确认预约
- `/watch/{videoId}`：视频播放页，播放前获取短期播放凭证
- `/admin/...`：后台管理页面，需要 JWT 和权限

## 共享能力

### 统一响应与错误

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "traceId": "8f3c..."
}
```

- HTTP 状态码表达协议层结果，业务码表达领域结果
- 分页统一为 `page`、`pageSize`、`total`、`records`
- 参数错误、未登录、无权限、资源不存在、状态冲突分别处理
- 所有响应带 trace ID，前端报错时提示用户可复制

### 登录与权限

- 后台和用户端共用 JWT，但权限边界不同
- 权限码按模块命名，例如 `order:read`、`stock:adjust`、`file:share`、`survey:publish`
- 前端路由守卫和按钮权限只改善体验，后端每个接口都要校验
- 公开短链不是后台权限，必须单独校验短码状态、过期时间和使用次数
- 管理员越权操作、库存调整、订单状态变化、问卷发布都写审计日志

### 幂等与事务

- 创建订单、支付回调、创建预约、提交问卷都使用幂等键或唯一约束
- 同一模块内的强一致操作使用本地事务
- 跨模块通知使用 outbox 或提交后事件，不把远程调用放进事务
- 定时任务必须可重复执行，清理和补偿逻辑不能依赖“只跑一次”

### 文件与短链

- `file_object` 保存对象键、原始文件名、大小、类型和哈希
- 对象存储只存内容，业务表只存 `fileId`
- `share_link` 统一管理短码、目标类型、过期时间、最大使用次数和状态
- 文件和问卷共用短链，不各自实现一套短码生成
- 预签名 URL 短期有效，不能把 MinIO 密钥和内部地址发给前端
- 视频源文件、封面和字幕也通过文件模块保存，视频模块只保存 `fileId`
- 视频播放使用短期 token 和后端 HLS 代理或 CDN 签名，私有桶不能公开读

### 通知与运营概览

- 订单支付、订单超时、预约提醒、问卷邀请通过 outbox 发送
- 运营概览展示今日订单、待发货、低库存、今日预约和问卷回收数
- 概览接口只做聚合展示，不承担对账职责
- 对账和异常巡检单独做后台任务

## 数据边界

- 一套 PostgreSQL 16 数据库，按模块使用表前缀：`sys_`、`file_`、`share_`、`pms_`、`inv_`、`oms_`、`bk_`、`sv_`、`video_`
- 主键统一使用 `bigserial` 或 `bigint identity`，对外暴露的短码和订单号单独生成，不直接暴露自增 ID
- 时间统一使用 `timestamptz` 存 UTC，半结构化配置使用 `jsonb`，金额使用整数分，文件大小使用字节
- 幂等写入优先使用唯一约束 + `ON CONFLICT`；活动任务可用部分唯一索引限制同一资源只有一个进行中任务
- 业务快照只增不改：订单项、库存流水、预约日志、问卷回答
- 跨模块只保存 ID，不建立跨模块级联删除
- 软删除用于业务数据，审计和流水只追加，不物理删除

## 统一验收

- [ ] `docker compose up -d` 可以启动 PostgreSQL、Redis、MinIO、后端和前端
- [ ] 有初始化 SQL、演示数据和至少两个测试账号
- [ ] 后台可以登录、分配角色、看到不同菜单和按钮权限
- [ ] 四个核心模块都能从菜单进入，并完成一条完整业务流程
- [ ] 公开短链可以访问文件分享页和问卷页，过期或撤销后立即失效
- [ ] 订单并发不超卖，支付回调幂等，超时取消释放库存
- [ ] 文件支持分片续传，越权下载和超限上传被拒绝
- [ ] 预约并发不重复占位，取消后容量正确释放
- [ ] 问卷发布后版本冻结，旧回答可解释，配额不被并发突破
- [ ] （可选）视频可以上传、转码、播放和续播，过期播放凭证被拒绝
- [ ] 关键操作有审计日志，异常有稳定错误码和 trace ID
- [ ] 至少有一组并发测试、集成测试和前端关键路径测试
- [ ] README 包含架构图、ER 图、模块说明、启动方式、测试方式和已知问题
- [ ] 有一份 5 分钟演示脚本和三张以上关键页面截图

## 推荐演示路径

1. 管理员登录，展示角色、菜单和运营概览
2. 创建商品和 SKU，调整库存并查看库存流水
3. 用户下单、模拟支付，展示订单状态和库存变化
4. 上传交付文件，创建短链，在无登录窗口打开并下载
5. 用户预约时段，再开一个窗口抢同一时段，展示冲突提示
6. 发布问卷，通过短链填写，查看统计和 CSV 导出
7. 上传一段视频，展示转码状态、HLS 播放、清晰度切换和续播（可选）
8. 展示审计日志、过期短链、重复支付回调等异常处理

演示时重点讲“为什么这样设计”和“如何证明正确”，不要只念功能列表。

## 简历表述

可以写成两条：

- 设计并实现模块化单体运营平台，包含订单库存、文件分享、预约和问卷四个核心模块，并提供视频播放扩展，统一后台登录、RBAC、审计和运营概览
- 通过条件更新与幂等约束解决库存超卖和重复支付，使用分片上传与短期签名 URL 实现大文件安全分享，使用唯一约束和事务处理预约并发，使用版本化问卷保证历史回答可解释

如果面试时间有限，优先讲订单库存和文件分享，因为这两个最能体现事务、并发、存储和安全边界。

## 裁剪原则

- 不做微服务、Kubernetes、真实支付、完整 BPMN、低代码平台和完整 IM
- 订单先做直接购买，购物车和优惠券后置
- 文件先做小文件，再做分片续传
- 预约先做单资源单时段，再做候补和多资源
- 问卷先做四种题型，再做跳题和复杂统计
- 视频先做点播 HLS、360p/720p 和短期播放凭证，直播、DRM 和自适应码率后置
- 对象存储首版用 MinIO 本地跑通，不接 OSS、STS 和 CDN；需要云部署时再替换为存储适配层
- 每个模块至少保留一个可验证的硬问题，否则就退化成普通 CRUD

## 与现有备选项目的关系

- `ADMIN_TEMPLATE.md` 是整套作品的壳和权限基础
- `ORDER_INVENTORY.md`、`FILE_SHARE.md`、`BOOKING.md`、`SURVEY.md` 是四个核心业务模块
- `VIDEO_PLAYER.md` 是可选的第五个模块，用于作品展示或课程回放，不阻塞核心四模块交付
- `APPROVAL_WORKFLOW.md` 可以作为后续扩展，例如退款审批或采购审批，但不放进首版主链路
- `CHAT_ROOM.md` 可以作为后续客服或站内沟通模块，也不放进首版主链路

先完成一套闭环，再增加模块。作品集的竞争力来自“能讲清楚一条完整链路”，不是模块数量。
